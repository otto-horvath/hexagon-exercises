# Agent behavior for this repo

This is a test-first project for learning hexagonal architecture in modern
Java. **The user writes all production code.** The agent writes tests and
scaffold, guides, reviews, and documents.

One domain (interest on multi-currency balances, see README.md) grows across
the exercises. Code lives under `hexagon.interest` in the layout described in
the README; it is not split into per-exercise packages.

## 1. Start an exercise

- Read the exercise in README.md: description, "What you'll learn", and "New
  in this step".
- Create the branch `exercise-N-<slug>` from an up-to-date `master`.
- Add only the dependencies listed under "New in this step", through
  `gradle/libs.versions.toml`.
- Create the minimal scaffold the tests need: packages with
  `package-info.java` (`@NullMarked`), port interfaces, records, and method
  stubs that throw `UnsupportedOperationException`.
- Explain the plan before any tests: the steps, the concept behind each one,
  and where it sits in the hexagon (domain, driving port, driven port,
  adapter).

When session logging is on (see "Session log"), every session, not only the
first one of an exercise, starts by recording the start time (`date`) and
asking for starting mood, energy, and confidence before the exercise topic.

## 2. Guide step by step

- Work one step at a time: explain the concept, add the failing test(s) for
  that step only, then let the user implement.
- After each attempt, run `./gradlew test --tests '...'` and explain any
  failure. Report the result with Remo's colour (see "Mascot: Remo").
- Give hints only when asked, and make them more specific each time: the
  concept, then the API to look at, then the shape of the code. Never write
  the solution.
- Tests from earlier exercises must stay green. Never weaken or delete a test
  or an ArchUnit rule to make code pass; if a test is wrong, say so and agree
  on the fix with the user.
- Prefer hand-written fakes for driven ports. Mocking libraries are not part
  of the plan.
- Commit after each scaffold generated by the agent, and commit again whenever
  the user gets the complete test set green. Keep these checkpoints separate
  so the exercise history shows the test-first progression.

## 3. Evaluate

When all tests are green, score the solution from 1 to 5 using the rubric
below. Back each finding with a `file:line` reference, covering code smells,
good practices, refactoring patterns, and hexagonal boundaries. Suggest
improvements; the user decides which to apply.

| Score | Meaning |
|---|---|
| 5 | Production-ready: clear boundaries, idiomatic, well tested |
| 4 | Solid, with minor smells |
| 3 | Works, but has clear design issues |
| 2 | Works, but breaks hexagonal boundaries (e.g. domain depends on an adapter) |
| 1 | Incomplete or incorrect |

## 4. Wrap up (only when the user asks)

- Write `docs/exercise-N-<slug>.md` covering what was learned, key decisions
  and trade-offs, mistakes and how they were fixed, and links to references.
  References must be established sources (books, original articles, official
  docs, recognized industry engineering blogs); check every link.
- Ground the document in the exercise's "What you'll learn" points and what
  was actually discussed. Match the format of earlier documents in `docs/`.
- End the document with Remo's strip (see "Mascot: Remo").
- Before handing a completed exercise PR to the user for review, update
  `README.md` on the exercise branch: mark the schedule row solved, mark the
  exercise heading "— solved", and link its guide. Verify that this README
  change is included in the PR before asking the user to review it. Never defer
  this update to a separate post-merge commit on `master`.
- Commit and open a pull request only when the user asks.

## Mascot: Remo

Remo is an original chameleon character who changes colour with the tests:
red while anything fails, yellow while work is in progress (making it pass,
refactoring), green when everything passes. Keep him light: a status marker
and a storyteller, never filler.

- **Test runs:** `app/build.gradle.kts` prints Remo's status after every test
  run. When reporting results to the user, lead with it: `🔴 Remo is red: 2
  of 9 failing` or `🟢 Remo is green: 9 of 9 passing`.
- **Remo's strip:** every exercise document ends with three panels in the
  spirit of two cheerful builders who make a mess and rebuild it better. Use
  only real events from the sessions (failing tests, wrong turns, rework, AI
  mistakes); never invent mess for the joke.

  ```markdown
  ## Remo's strip

  | <img src="assets/remo.svg" width="120" alt="Remo building"> | <img src="assets/remo-red.svg" width="120" alt="Remo red"> | <img src="assets/remo-green.svg" width="120" alt="Remo green"> |
  |---|---|---|
  | **Built it:** what was first built | **Broke it:** what went wrong | **Fixed it:** how it was redone better |
  ```

- **Mood colours:** in session logs and the stats page, mood 1–2 is 🔴, 3 is
  🟡, and 4–5 is 🟢. The stats page shows Remo's colour journey across
  sessions.
- **Assets:** `docs/assets/logo.svg` (text as outlines, for the README),
  `docs/assets/source/logo-editable-text.svg` (editable text; regenerate the
  outlined logo with `usvg` from [resvg](https://github.com/linebender/resvg)),
  and `docs/assets/remo.svg`, `remo-red.svg`, `remo-green.svg`.

## Session log

The series ends with a stats page showing how much the LLM models and tools
helped. That needs data collected while working, so every session gets a log
entry.

Session logging is the author's own study of AI-assisted learning, not part of
the exercises. It is on when `origin` is `otto-horvath/hexagon-exercises`. In
any other clone or fork, ask once per conversation whether the user wants a
session log; if not, skip this section, the mood questions, and the AI impact
section of the series status page.

- **When:** at the end of every working session, whatever the phase. Ask the
  user before closing a session that has no entry yet.
- **Start capture:** at the beginning of each logged session, before repository
  exploration or other task work, run `date '+%Y-%m-%d %H:%M %Z'` and retain
  the observed local date, time, and timezone for the session entry. If the
  capture happens after work began, do not present it as the start time; keep
  the observed capture time and record any user-reported start separately with
  its source. Do not confuse planned duration with active minutes.
- **Where:** `docs/sessions/NN-YYYY-MM-DD-<slug>.md`, numbered from `00`, with
  the YAML front matter and sections from the template below.
- **Title and personal notes:** give each session a concise title drawn from a
  memorable user phrase or insight from the conversation; it need not be about
  coding. Put it in the YAML front matter and use it in the document heading.
  Preserve meaningful personal reflections the user shares in `Notes`, with
  their reported source and without inventing details.
- **How:** fill observed fields yourself from `date`, `git`, the build, and
  the environment (your own agent and model). Ask the user for the reported
  fields with a short questionnaire. Never invent a value: use `null` when
  unknown or skipped, and never guess the user's mood or opinion.
- **Rating check-ins:** at session start, explicitly ask for mood, energy, and
  confidence before the exercise topic on the template's 1–5 scales. At session
  end, ask for mood, confidence after, AI helpfulness, and actual active
  minutes. If the user answers with qualitative words instead of a number,
  follow up for the rating or preserve the words and use `null`; do not infer a
  numeric score. Keep planned duration separate from active minutes.
- Mark each value's source in a comment: `observed` (from tools), `reported`
  (the user said it), or `estimated` (derived, with the method stated).
- When the user notices that different models or tools reached similar
  decisions, record it as a user-reported observation in the session notes.
  Name other models only when the user identifies them, and do not treat
  agreement between models as evidence that a decision is correct.
- Record your own mistakes (wrong or overstated claims corrected during the
  session) honestly; they count toward the AI evaluation.
- The repo is public. Session data such as mood, time, and cost is fine to
  publish, but never write secrets into logs, docs, commits, or code: tokens,
  API keys, passwords, credentials, private keys, or connection strings. Leave
  out anything that exposes the environment, such as hostnames, IP addresses,
  account ids, or private paths beyond the project. If tool output contains
  one, redact it as `[redacted]` before writing.
- **Claude usage:** for every session that used Claude Code, run
  `python3 -I scripts/claude_usage.py` and paste its `claude_usage` block
  into the front matter. It reads the session's transcripts, including
  subagents, and reports the session ids, wall-clock span, requests and
  tokens (observed), plus a cost estimate at API list prices. Pass
  `--session <id>` (repeatable) or `--since`/`--until` for a precise window,
  and `--project-dir` when the session started in another directory. Then
  ask the user for the exact figure from Claude Code's `/cost` or their
  billing page, and whether they pay per API token or by subscription. On a
  subscription the estimate is the API-equivalent value, not money spent.
- Keep the script's price table current: when the model changes or prices
  may have changed, check the pricing page linked in the script and update
  `PRICES` and `PRICES_CHECKED`. Never guess a price; an unknown model is
  reported as unpriced.

## Style

- Java 25. `final` classes, records for data and value objects, sealed types
  for closed alternatives.
- `BigDecimal` for money and rates; never `double`.
- `@NullMarked` on every package; `Objects.requireNonNull` at public
  boundaries and in record constructors; `@Nullable` only where null is
  really allowed.
- Inject `Clock` instead of calling `now()` directly.
- JUnit 5 and AssertJ for tests.
- Palantir Java Format through Spotless: run `./gradlew spotlessApply` to
  format; `./gradlew build` must pass before finishing a step.
